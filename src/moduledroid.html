ModuleDroid

I designed a modular library for three routine Android tasks: moving between screens, saving preferences and restoring screen state.

Three plugins, one after another

Browse all the examples without switching tabs.

NavigatorConfiguratorRestorer

Simplified usage snippets. Imports, the Activity class and framework initialisation are omitted.

Navigator

Receive a result from another screen.

Without the pluginKotlin / Android
private val editor = registerForActivityResult(
    ActivityResultContracts.StartActivityForResult()
) { result ->
    if (result.resultCode == RESULT_OK) {
        val name = result.data?.getStringExtra("name")
        if (name != null) showName(name)
    }
}

fun openEditor() {
    editor.launch(Intent(this, EditActivity::class.java))
}

Register the launcher, launch the Intent and extract the result.

With NavigatorModuleDroid
Navigate.toReturn(EditActivity::class).andThen {
    val name = Navigate.getResult<String>("name")
    if (name != null) showName(name)
}

Open the screen and define what happens on return.

This example shows the caller; the editing screen is omitted in both versions. Navigator encapsulates navigation and result handling in a chained call.

View plugin API

Configurator

Save and read a preference.

Without the pluginKotlin / Android
val preferences = getSharedPreferences(
    "settings", Context.MODE_PRIVATE
)
preferences.edit()
    .putBoolean("notifications", true)
    .apply()

val enabled = preferences.getBoolean(
    "notifications", false
)

Access the preference store and manage its editor.

With ConfiguratorModuleDroid
Configurator.set("notifications", true)

val enabled = Configurator.get(
    "notifications", false
)

Read and write through a typed facade.

Encapsulates SharedPreferences and its editor. The plugin also supports change subscriptions and a generated settings screen.

View plugin API

Restorer

Keep a counter when the screen rotates.

Without the pluginKotlin / Android
var count = 0

override fun onCreate(state: Bundle?) {
    super.onCreate(state)
    count = state?.getInt("count") ?: 0
}

override fun onSaveInstanceState(out: Bundle) {
    out.putInt("count", count)
    super.onSaveInstanceState(out)
}

Save and retrieve the field in lifecycle callbacks.

With RestorerModuleDroid
@Restore
var count = 0

Declare which field should keep its value.

The plugin connects saving and restoration to the lifecycle through annotations. This example is limited to recreation such as rotation; it does not establish equivalence with Bundle after process death.

The challenge

Navigation, preferences and Activity recreation often scatter supporting code throughout an app. The goal: encapsulate it and make it reusable.

My contribution

I designed and implemented the microkernel, its facades and all three plugins, including lifecycle management and a sample app to compare the development approaches.

More engineering detail

Extensible architecture. A core, facades and a data bus separate responsibilities and support plugins. Initialisation uses manifest metadata.

Android integration. Application and ActivityLifecycleCallbacks connect plugins to the app lifecycle.

Validation. Over one hundred instrumented tests reported in the project documentation. Distribution designed around JitPack.
